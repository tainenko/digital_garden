# 時序資料庫設計

## 場景需求

典型案例：每 10ms 到達一批 metrics 的大規模監控系統
- **Write-heavy**：海量數據持續寫入，寫入吞吐量是第一要務
- **時間範圍查詢**：「過去 1 小時 / 24 小時 / 1 個月」的聚合查詢
- **標籤過濾**：按 metric name + tag 組合（如 `cpu{host=A, region=us}`）過濾

---

## 主流方案比較

### TimescaleDB（PostgreSQL 擴展）

- 在 PostgreSQL 上建立 `hypertable`，內部切分成 time-based chunks（仍支援 index、trigger、UPSERT）
- 效能：比原生 PostgreSQL **快 20×**，可達 **110萬 metrics/s**；支援 **50K 分區/節點**
- 優勢：SQL 相容、生態成熟、無需全新學習曲線

### Pinterest Goku（自研，Go + Facebook Gorilla）

起因：OpenTSDB 在規模下效能退化，Pinterest 自行研發

**架構特點：**
- **記憶體層**：Facebook Gorilla 壓縮引擎，存放最近 24 小時熱資料，**12× 壓縮比**
- **磁碟層**：長期冷資料（降採樣 + 壓縮）
- **倒排索引**：支援高效 tag 組合查詢
- **兩層分片**：按 metric name 分片 → 再按 tag 組合分片
- **計算下推**：查詢在葉節點並行計算後再聚合（Scatter-Gather 模式），避免中央化瓶頸

---

## 通用設計原則

### 寫入路徑
```
Producer → WAL（持久化）→ In-Memory Buffer（熱層）→ Compaction → Disk（冷層）
```
類似 LSM Tree 的分層設計：寫入先到記憶體，定期 flush + compaction 到磁碟

### 查詢路徑
```
Query → 路由到對應分片節點 → 葉節點並行聚合 → 結果合併回傳
```

### 資料生命週期
| 時間範圍 | 儲存層 | 解析度 |
|---------|--------|--------|
| 0–24h | 記憶體（Gorilla） | 原始精度（每10ms）|
| 1–30d | 快速磁碟 | 1分鐘聚合 |
| 30d+ | 冷儲存 | 1小時聚合（降採樣）|

---

## 關鍵技術點

- **Gorilla 壓縮**：Facebook 開源的時序壓縮算法，利用時間戳 delta-of-delta + 值 XOR 實現 12× 壓縮
- **倒排索引**：`(metric, tag set) → series ID`，支援快速 tag 過濾
- **降採樣（Downsampling）**：長期資料以更大時間粒度存儲，節省空間同時保留趨勢
