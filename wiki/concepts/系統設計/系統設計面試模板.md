# 系統設計面試模板

[[Aritra Sen]] 提出的系統設計面試六步結構，在 45–60 分鐘內確保不遺漏關鍵環節。

> 模板的核心價值：時間管理 + 不遺漏 + 設計可辯護

---

## 六個步驟

### Step 1：需求釐清（Requirements）

分兩類：

**Functional Requirements（功能需求）**
- 這個系統要做什麼？
- 與面試官確認優先範圍（如「Design Instagram」→ 縮窄到「照片分享」）
- 確認面試官最在意哪些功能

**Non-functional Requirements（非功能需求）**
- 讀重還是寫重？
- 需要強一致性還是最終一致性？
- 延遲/可用性要求為何？
- 安全/隱私考量？

見[[Functional vs Non-functional Requirements]]。

---

### Step 2：Back-of-the-Envelope 估算

量化非功能需求，驅動後續所有架構選型。

- **DAU**（每日活躍用戶）
- **讀/寫頻率**（每天幾次操作）→ 判斷讀重 or 寫重
- **儲存需求**（平均寫入大小 × 寫入次數 × 時間）→ 至少估1年
- **網路頻寬**（每秒請求數峰值）→ 決定是否需要 CDN/Cache

見[[Back-of-the-Envelope 估算]]。

---

### Step 3：API 設計與資料表示

設計對外 API，決定如何暴露功能需求。

- 選擇 API 協定：REST / gRPC / GraphQL
- 定義主要 endpoints（命名與格式需一致）
- 在此引入 Pagination（讀重 API）、Rate Limiting（安全）等

---

### Step 4：高層設計（High-level Design）

畫出整體架構概覽，不要太早深入細節。

- Load Balancer
- 各服務模組
- 資料庫
- Queue
- Cache

**警告**：先把全局畫完，再深入個別元件。容易犯的錯是在某個區塊講太久，導致後面沒時間。

---

### Step 5：資料庫設計（Database Design）

最重要的深入環節之一。

- Schema 設計
- SQL vs NoSQL 選型（見[[SQL vs NoSQL 選型框架]]）
- Replication 策略
- Sharding 策略（如需要）
- Object Storage（圖片/影片/Blob）

**注意**：不需要寫 SQL query 或 UML，保持高層次。

---

### Step 6：詳細設計選型（Detailed Design Choices）

辯護其他架構決策：

- 認證/授權
- 負載均衡策略
- 快取策略（Cache eviction policy、Cache aside vs Write-through）
- CDN 使用時機
- 資料保留策略
- Trade-off 說明

**必須能辯護每一個選擇**。設計對但無法解釋 = 無效。

---

## 常見陷阱

| 陷阱 | 說明 |
|------|------|
| 過早深入 | 在高層設計前就講細節，導致沒時間畫全局 |
| 需求不清 | 沒和面試官確認優先範圍，設計方向跑偏 |
| 估算跳過 | 跳過估算，導致後續選型缺乏依據 |
| 設計不辯護 | 說「我選 NoSQL」但無法解釋為什麼 |
