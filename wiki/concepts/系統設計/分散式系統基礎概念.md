# 分散式系統基礎概念

系統設計面試的地基。[[Aritra Sen]] 建議在學習任何模板或練題之前，先把這些概念搞清楚。

---

## 核心概念清單

### 擴展（Scaling）
- **垂直擴展（Scale Up）**：加強單台機器規格
- **水平擴展（Scale Out）**：增加更多機器
- 分散式系統幾乎都依賴水平擴展

### 負載均衡（Load Balancing）
- 將請求分散到多台伺服器
- 演算法：Round Robin、Least Connections、IP Hash
- 實現高可用（HA）的基礎元件

### 一致性雜湊（Consistent Hashing）
- 解決分散式快取/資料庫節點增減時的再分配問題
- 最小化節點變動時的 key 重新映射範圍

### CAP 定理
分散式系統只能同時保證三者中的兩者：
- **C**onsistency（一致性）：所有節點看到相同資料
- **A**vailability（可用性）：每個請求都有回應
- **P**artition Tolerance（分區容忍）：網路分區時仍能運作

> 實務上 P 幾乎必須保留，所以選擇通常是 **CP vs AP**。

| 類型 | 取捨 | 代表系統 |
|------|------|---------|
| CP | 犧牲可用性保一致性 | HBase、ZooKeeper |
| AP | 犧牲強一致性保可用性 | Cassandra、DynamoDB |

### CDN（內容分發網路）
- 把靜態資源放在離用戶近的邊緣節點
- 降低延遲、減少源站負載
- 影片/圖片/靜態網頁的標配

### 快取（Caching）
- 把高頻讀取的資料放在記憶體層（如 Redis、Memcached）
- 策略：Cache-Aside（讀時填充）、Write-Through（寫時同步）
- 注意快取失效（eviction）與快取穿透問題

### Failover 與 Replication
- **Failover**：主節點失效時自動切換到備援節點
- **Replication**：資料複製到多個節點
  - 同步複製：強一致，延遲較高
  - 非同步複製：最終一致，延遲較低

### API 協定
| 協定 | 特點 | 適用場景 |
|------|------|---------|
| REST | 無狀態、通用、易理解 | 大多數 Web API |
| gRPC | 高效能、強型別、二進制 | 微服務內部通訊 |
| GraphQL | 客戶端主導查詢 | 複雜前端查詢需求 |

### Polling / Long Polling / WebSocket
- **Polling**：客戶端定時問「有沒有新資料？」
- **Long Polling**：伺服器保持連線直到有資料才回應
- **WebSocket**：雙向持久連線，實時通訊首選

### Queue（訊息佇列）⭐
- 解耦生產者與消費者，非同步處理高頻請求
- 兩種模型：
  - **Message Queue**：一個消息只被一個消費者處理（點對點）
  - **Pub-Sub**：一個消息廣播給所有訂閱者
- 使用時機：削峰填谷、任務異步化、服務解耦

> Aritra：「Queues are OP。理解何時用、為何用，是面試的大加分項。」
