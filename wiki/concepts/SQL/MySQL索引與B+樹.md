# MySQL 索引與 B+ 樹

MySQL（InnoDB）索引的核心資料結構與設計原理，後端面試高頻題。

## 為何用 B+ 樹（而非 B 樹 / Hash / 紅黑樹）
資料庫真正的瓶頸是**磁碟 I/O**，B+ 樹的設計全為了「用最少的磁碟讀取找到資料」：

- **非葉節點不存資料、只存索引鍵**：相同大小的磁碟塊（page）能放入更多索引項，使樹更「矮胖」。3 層 B+ 樹約可容納 **~17 億筆**記錄，一次查詢通常只需 2–3 次磁碟 I/O。
- **葉節點以鏈結串列相連**：天然支援**範圍查詢**（`BETWEEN` / `>` / `ORDER BY`），順序掃描即可。
- **充分利用磁碟預讀**：每個節點填滿一個 page，貼合作業系統預讀機制。

對照：
- **Hash 索引**：O(1) 等值查詢快，但**不支援範圍查詢與排序**。
- **B 樹**：非葉節點也存資料，單 page 索引項較少 → 樹更高 → I/O 更多。
- **紅黑樹**：二元結構樹高過大，磁碟場景 I/O 次數爆炸。

## InnoDB vs MyISAM
| 面向 | InnoDB | MyISAM |
|------|--------|--------|
| 交易 | 支援 | 不支援 |
| 鎖粒度 | 行鎖 | 表鎖 |
| 外鍵 | 支援 | 不支援 |
| 崩潰恢復 | 自動 | 需手動修復 |
| 全文索引 | （舊版不支援）| 支援 |
| 索引結構 | 聚簇索引（資料即索引）| 非聚簇（索引與資料分離）|

## 索引類型與關鍵概念
- **聚簇索引（Clustered Index）**：以主鍵組織，葉節點直接存**整行資料**。InnoDB 一張表只有一個。若無主鍵會選唯一索引、再無則隱藏 rowid。
- **二級索引 / 非聚簇索引（Secondary Index）**：葉節點存「索引欄 + 主鍵值」。查非索引欄需拿主鍵**回表**到聚簇索引再查一次。
- **覆蓋索引（Covering Index）**：查詢需要的欄位**全部存在於索引中**，免回表，是重要的效能優化（`EXPLAIN` 出現 `Using index`）。
- **最左前綴原則（Leftmost Prefix）**：複合索引 `(a, b, c)` 只能有效支援以 `a`、`(a,b)`、`(a,b,c)` 起頭的查詢；單獨查 `b` 或 `c` 無法走索引。範圍查詢（如 `b > x`）之後的欄位也無法再用索引。
