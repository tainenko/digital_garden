# 12306 系統設計面試完整解題框架

極海Channel（前阿里巴巴工程師）分析：12306 是中國技術面試中最常見的系統設計題之一，因為它具備「全球級高難度」的技術挑戰——節假日峰值時，幾億人同時搶票，是真實存在的地獄級高並發場景。

> 「12306 的設計難點，幾乎涵蓋了分散式系統所有核心問題。能說清楚 12306，你的系統設計就過了 80%。」

---

## 面試時第一步：釐清需求和規模

不要上來就設計，先確認邊界：

```
功能性需求（Functional Requirements）：
- 用戶查詢列車和座位（高頻讀）
- 用戶購票（高並發寫）
- 訂單管理（查看、退改簽）
- 支付（集成第三方）

非功能性需求（Non-functional Requirements）：
- 平日 QPS：查詢 10 萬，購票 1 萬
- 節假日峰值 QPS：查詢 100 萬，購票 30 萬（春節期間可能更高）
- 可用性：99.99%（全年停機不超過 1 小時）
- 一致性：強一致性（不能超賣）
- 延遲：查詢 P99 < 200ms，購票 P99 < 2s
```

---

## 12306 的三大核心技術難點

### 難點一：超高並發下的庫存不超賣

這是最核心的挑戰。春節搶票時，1 秒內可能有 10 萬人同時搶同一張票（G1 次復興號，一等座只有 70 個）。

#### 解法：分層庫存架構

```
Level 1：應用層預扣（Local Cache）
├── 每個應用節點在內存中維護一個「粗粒度庫存」
├── 當本地庫存扣減到 0 → 直接拒絕，不打到 DB
└── 優點：大量請求在應用層被擋掉

Level 2：分散式緩存（Redis）
├── 精確庫存存在 Redis
├── 用 Lua Script 保證原子操作（DECR + 判斷 >= 0）
└── 優點：單 Redis 可以抗幾十萬 QPS

Level 3：資料庫（MySQL）
├── 最終一致性寫入
├── 用 SELECT ... FOR UPDATE 保證強一致
└── 只有真正「搶到票」的請求才到達 DB

流程：
用戶請求 → 本地庫存判斷（無 IO） → Redis 原子扣減 → 非同步寫 DB
```

#### Redis Lua Script 原子庫存扣減

```lua
-- inventory_deduct.lua
local key = KEYS[1]          -- 庫存 key，例如 "train:G1:seat:1A:2024-02-10"
local quantity = tonumber(ARGV[1])

local current = tonumber(redis.call('GET', key))
if current == nil then
    return -1   -- key 不存在
end

if current < quantity then
    return 0    -- 庫存不足
end

redis.call('DECRBY', key, quantity)
return 1        -- 扣減成功
```

這個 Lua Script 保證了「查詢庫存」和「扣減庫存」是原子操作，不會有競態條件。

### 難點二：座位的複雜性——區間座位問題

12306 的座位不是簡單的「有/沒有」，而是**區間**問題：

```
北京 → 上海 的高鐵，途經：
北京 → 天津（區間一）
天津 → 濟南（區間二）
濟南 → 徐州（區間三）
徐州 → 南京（區間四）
南京 → 上海（區間五）

座位 1A 的狀態：
- 北京到天津：被張三買走
- 天津到濟南：空閒
- 濟南到上海：被李四買走（從濟南上車到上海）

如果王五要買「天津到濟南」，座位 1A 可以賣！
但如果王五要買「天津到徐州」，跨了「濟南-徐州」這段，座位 1A 不能賣。
```

#### 解法：位元圖（Bitmap）表示區間佔用

```
將每個站點編號（北京=1，天津=2，濟南=3，徐州=4，南京=5，上海=6）

座位 1A 的佔用狀態用 Bitmap 表示：
位置： 1  2  3  4  5  6
       北 天 濟 徐 南 上
Bitmap：1  0  0  1  1  1

說明：1 表示這個「出發點」的座位被佔用
（張三從北京出發，所以位置 1=1；李四從濟南出發，所以位置 3、4、5=1）

查詢「天津到徐州」是否可用：
需要檢查位置 2、3 是否都為 0
Bitmap[2] = 0，Bitmap[3] = 0 → 可以賣！

查詢「天津到南京」是否可用：
需要檢查位置 2、3、4 是否都為 0
Bitmap[3] = 1 → 不能賣！
```

#### 實作：用 Integer 的 bit 表示區間

```java
// 每個座位用一個 Integer 存儲區間佔用情況
// 假設最多 32 個站點（一列火車通常不超過 20 個站）
public class SeatBitmap {
    
    // 購票：標記 fromStation 到 toStation 的位元
    public static int bookSeat(int currentBitmap, int from, int to) {
        // 構建需要標記的 mask
        int mask = 0;
        for (int i = from; i < to; i++) {
            mask |= (1 << i);
        }
        
        // 檢查是否有衝突
        if ((currentBitmap & mask) != 0) {
            throw new IllegalStateException("座位已被佔用");
        }
        
        return currentBitmap | mask;
    }
    
    // 查詢：檢查 fromStation 到 toStation 是否可購買
    public static boolean isAvailable(int currentBitmap, int from, int to) {
        int mask = 0;
        for (int i = from; i < to; i++) {
            mask |= (1 << i);
        }
        return (currentBitmap & mask) == 0;
    }
}
```

### 難點三：查詢優化——縮短搶票路徑

購票流程中，最大的延遲來源是「查詢哪個座位可以買」。

#### 解法：反轉索引（Inverted Index）

```
不要以「座位」為索引，而是以「區間組合」為索引：

傳統索引：
  座位 1A → {北京-天津: 已佔, 天津-濟南: 空, ...}
  座位 1B → {北京-天津: 空, 天津-濟南: 空, ...}
  ...
（查詢「天津到濟南」需要掃描所有座位）

反轉索引：
  天津-濟南 → [座位 1A, 座位 2C, 座位 3B, ...]（可用座位列表）
  北京-上海 → [座位 4D, 座位 5A, ...]
（查詢「天津到濟南」直接拿到可用座位列表，O(1)）
```

#### 配合 Redis 做搶票池

```
Redis Key：train:G1:date:20240210:segment:TJ-JN
Redis Value：List of available seats（座位 ID 列表）

購票流程：
1. RPOP train:G1:date:20240210:segment:TJ-JN
   （從列表彈出一個座位 ID，O(1)，原子操作）
2. 拿到座位 ID 後，非同步更新 DB
3. 如果 5 分鐘內未支付，把座位 ID 推回 Redis

這樣整個「搶到座位」的操作是 O(1) 的 Redis 操作。
```

## 高可用架構設計

```
用戶層
  ↓
CDN（靜態資源、時刻表查詢）
  ↓
API Gateway（限流、鑑權）
  ↓ 
應用服務集群（水平擴展，無狀態）
  ↓
                    ↓
             Redis Cluster          MySQL 主從集群
         （庫存、搶票池、Session）  （訂單、用戶資料）
                    ↓
             消息隊列（Kafka）
                    ↓
             非同步處理（訂單創建、支付通知、退票）
```

### 限流策略

```
三層限流：

1. 閘道層（API Gateway）：
   - 每個用戶每秒最多 1 次購票請求（令牌桶）
   - 每個 IP 每秒最多 10 次查詢

2. 應用層（用戶行為限流）：
   - 同一用戶同一班次同一區間，60 秒內只能搶一次
   - 已有未支付訂單的用戶，不能再搶票

3. 資料庫層（後備）：
   - SELECT ... FOR UPDATE 保證最終一致性
```

## 面試中如何組織這些知識

```
回答結構（10-15 分鐘）：

1. 釐清需求（2 分鐘）
   → 功能性/非功能性需求，特別是規模數字

2. 識別核心挑戰（1 分鐘）
   → 「這個系統最難的是三件事：超賣問題、區間座位問題、查詢性能」

3. 逐一解決核心挑戰（8-10 分鐘）
   → 超賣：分層庫存 + Redis Lua Script
   → 區間座位：Bitmap 表示法
   → 查詢性能：反轉索引 + Redis 搶票池

4. 高可用設計（2 分鐘）
   → 限流策略
   → 降級方案（Redis 掛了怎麼辦）
   → 監控告警

5. 主動說出取捨（1 分鐘）
   → 「我選擇犧牲強一致性換取性能，在搶票環節允許短暫超賣後補償」
   → 「我選擇在 Redis 層處理庫存而非 DB 層，原因是...」
```
