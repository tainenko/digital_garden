# 九分鐘看懂系統設計面試

極海Channel 的系統設計面試入門影片，用 9 分鐘說明系統設計面試的本質、常見題型、以及通用的回答框架。這是所有系統設計面試準備的起點。

> 「系統設計面試考察的不是你能不能設計出完美的系統，而是你能不能像一個有經驗的工程師一樣思考問題。」

---

## 什麼是系統設計面試

系統設計面試的本質：**在有限的時間內，用對話的方式展示你設計複雜系統的能力**。

```
不是：
× 給你一張白紙，讓你畫出完整的系統架構圖
× 考察你知不知道某個技術的具體參數
× 要求你設計出「最好」的系統

而是：
✓ 觀察你如何提問、釐清需求
✓ 觀察你如何識別核心挑戰
✓ 觀察你如何做取捨決策
✓ 觀察你有沒有考慮到邊界情況
```

## 系統設計面試的五個步驟

### Step 1：釐清需求（2-5 分鐘）

這是最容易被新手忽略的步驟，也是最能展示資深感的步驟。

**功能性需求（What to build）**：
```
必問問題：
- 系統的核心功能是什麼？（用 1-2 句說清楚）
- 有哪些邊緣功能？（現在要設計還是以後再說？）
- 用戶操作的主流程是什麼？
```

**非功能性需求（How well to build it）**：
```
必問問題：
- 有多少用戶？日活多少？
- 讀多還是寫多？讀寫比例大概是多少？
- 對可用性的要求是多少？（99.9%? 99.99%?）
- 對一致性的要求是強一致還是最終一致？
- 延遲要求是多少？（P99 < 100ms?）
- 數據規模有多大？需要存幾年的數據？
```

**明確範圍**：
```
「好，讓我確認一下我們要設計的範圍：
 核心功能是 [X]，暫時不考慮 [Y]。
 規模是：DAU 1000 萬，讀 QPS 5 萬，寫 QPS 5000，
 可用性要求 99.99%，一致性要求最終一致。
 是這樣嗎？」
```

---

### Step 2：估算規模（1-2 分鐘）

背景計算，幫助後面的架構選擇：

```
流量估算：
- QPS = DAU × 每日請求次數 ÷ 86400 秒
- 峰值 QPS ≈ 平均 QPS × 2-3 倍

存儲估算：
- 每天新增數據量 = 每天寫入量 × 每條記錄大小
- 5 年存儲 = 每天數據量 × 365 × 5

帶寬估算：
- 出站帶寬 = 讀 QPS × 每次響應大小

常用數字記憶：
- 1 天 = 86400 秒（約等於 10^5）
- 1 年 = 3000 萬秒（約等於 3 × 10^7）
- 1 GB = 10^9 bytes
- 1 MySQL 機器 = 約 3000 QPS（讀），500-1000 QPS（寫）
- 1 Redis 機器 = 約 10 萬 QPS
```

---

### Step 3：高層架構設計（3-5 分鐘）

用最簡單的方式畫出系統的大框架：

```
基本組件（99% 的系統都需要）：
- 客戶端（Web / Mobile）
- DNS + CDN（靜態資源）
- 負載均衡（Load Balancer）
- 應用服務器（Stateless）
- 資料庫（讀寫分離）
- 緩存（Redis）
- 消息隊列（非同步任務）

根據場景加的：
- 文件存儲（S3 / OSS）
- 全文搜索（Elasticsearch）
- 推薦系統（ML 推理服務）
- 實時流處理（Kafka + Flink）
```

**畫圖技巧**：先畫主流程，再加優化組件。

```
第一版（MVP）：
用戶 → LB → App Server → MySQL

第二版（加緩存）：
用戶 → LB → App Server → Redis → MySQL

第三版（讀寫分離）：
用戶 → LB → App Server → Redis → MySQL Master（寫）
                                  → MySQL Slave（讀）
```

---

### Step 4：深入核心組件（3-5 分鐘）

面試官通常會引導你深入某個組件。你也可以主動說：

```
「這個系統最有意思的設計挑戰是 [X]，我來詳細說一下我的設計。」
```

**常見的深入方向**：

#### 資料庫設計
```
Schema 設計：
- 選擇合適的資料類型（INT vs BIGINT，VARCHAR vs TEXT）
- 索引設計（主鍵索引、聯合索引、覆蓋索引）
- 分表策略（水平分表：按 user_id 取模；垂直分表：冷熱分離）

CAP 取捨：
- 強一致性：主從同步，犧牲可用性（主庫掛了不能寫）
- 最終一致性：非同步複製，允許短暫不一致，但高可用
```

#### 緩存設計
```
緩存策略：
- Cache Aside（最常見）：應用自己管理緩存
- Read Through：緩存層自動從 DB 填充
- Write Through：同時寫緩存和 DB
- Write Behind：先寫緩存，非同步同步到 DB

緩存問題：
- 緩存穿透：查詢不存在的數據 → 用 Bloom Filter 擋
- 緩存擊穿：熱點 key 過期時大量請求直打 DB → 用互斥鎖/提前續期
- 緩存雪崩：大量 key 同時過期 → 隨機化 TTL
```

#### 消息隊列設計
```
為什麼用消息隊列：
- 解耦：生產者和消費者獨立擴展
- 削峰：高峰期把請求排隊，平滑消費
- 非同步：不需要立刻得到結果的操作放後台

消費語義：
- At Most Once：可能丟消息（適合：日誌）
- At Least Once：可能重複（適合：支付，需要冪等）
- Exactly Once：最難實現，一般用業務冪等代替
```

### Step 5：討論取捨和進一步優化（2-3 分鐘）

這一步是區分 P6 和 P7 的關鍵。

```
主動說出你沒有解決的問題：
「這個設計的瓶頸是 [X]，如果規模再大 10 倍，
 我會考慮 [Y] 方案來解決它。」

主動說出你做的取捨：
「我選擇最終一致性而不是強一致性，
 因為這個場景下讀到稍舊的數據是可以接受的，
 而強一致性會損害 50% 的讀性能。」

主動問面試官：
「您認為這個設計中哪個地方最值得深入討論？」
```

## 常見系統設計題型和核心挑戰

| 題目 | 核心挑戰 | 關鍵技術 |
|------|---------|---------|
| 設計短網址系統 | 全局唯一 ID 生成、讀多寫少 | 雪花算法、Base62 編碼、CDN |
| 設計社交 Feed | 推模型 vs 拉模型、熱門用戶 | Fanout、Redis Sorted Set |
| 設計搶購系統 | 庫存超賣、高並發寫 | Redis Lua Script、消息隊列 |
| 設計聊天系統 | 實時性、消息順序 | WebSocket、Kafka、全局序號 |
| 設計 Google Drive | 大文件上傳、秒傳 | 分塊上傳、MD5 去重、對象存儲 |
| 設計搜尋引擎 | 倒排索引、排名算法 | Elasticsearch、PageRank |
| 設計打車系統 | 地理位置匹配、實時狀態 | GeoHash、WebSocket、一致性哈希 |

## 9 分鐘學會的核心語感

在系統設計面試中，有幾個說法能立刻展示你的「老手感」：

```
展示問題意識：
「這裡有一個潛在的競態條件...」
「如果並發很高，這裡會成為瓶頸...」

展示取捨思維：
「我可以用 A 或 B 方案，A 的優點是...缺點是...
 在這個場景下，我選 A，因為...」

展示規模意識：
「這個設計在 1 萬 QPS 下沒問題，
 如果要支持 10 萬 QPS，需要在 [X] 加一層...」

展示邊界意識：
「這個方案假設了 [Y]，如果 [Y] 不成立，
 我們需要額外處理 [Z]。」
```
