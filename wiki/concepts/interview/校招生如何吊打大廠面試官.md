# 校招生如何吊打大廠面試官：算法與基礎知識的制勝策略

極海Channel 揭示了一個反直覺的現象：校招生在算法題上「吊打」面試官，基礎知識「信手拈來」。這不是偶然——這是系統性準備的結果。

> 「大廠面試官每天面試，自己不一定還記得那些算法題。但候選人如果刷了 300 題，可以比面試官更熟。這是校招的機會窗口。」

---

## 為什麼校招候選人有機會「吊打」面試官

面試官的困境：
```
面試官（工作 5-8 年的工程師）：
- 日常工作不再手寫算法
- LeetCode 可能上次刷是 3 年前
- 對基礎 CS 理論的記憶在退化

校招候選人（近期畢業生）：
- 最近幾個月系統刷題
- 剛學完操作系統/計算機網絡/編譯原理
- 基礎理論記憶最新鮮
```

**這個窗口只存在於校招。工作幾年後，你的算法能力也會退化。**

## 校招面試的三個核心模塊

### 模塊一：算法與資料結構（佔比最重）

#### 刷題路徑（3-4 個月版本）

```
Phase 1（第 1-2 週）：基礎數據結構
- Array、String、LinkedList 操作
- Stack、Queue 的應用
- Binary Tree 的 DFS/BFS
目標題數：50 題

Phase 2（第 3-5 週）：核心算法模式
- Two Pointers（雙指針）
- Sliding Window（滑動視窗）
- Binary Search（二分搜索）
- Recursion + Backtracking（回溯）
目標題數：累計 100 題

Phase 3（第 6-8 週）：中階難度
- Dynamic Programming（基礎 DP）
- Graph（BFS/DFS/Topological Sort）
- Heap / Priority Queue
目標題數：累計 180 題

Phase 4（第 9-12 週）：高頻題與 Hard
- Top 100 高頻面試題
- DP 進階（背包問題、區間 DP）
- 系統設計輕量版
目標題數：累計 280-350 題
```

#### 刷題不是「數量」，是「深度」

```
錯誤刷題方式：
看題 → 不會 → 直接看答案 → 抄一遍 → 下一題

正確刷題方式：
看題 → 思考 15-25 分鐘（真的嘗試） → 寫出來 → 
提交 → 看官方解答比較差異 → 
理解 2-3 種不同解法 → 
1 週後不看解法重做一次
```

**一道題真正理解 > 三道題只是抄過。**

#### 面試中算法題的回答框架

```
1. 確認理解（1-2 分鐘）：
「讓我確認一下需求：輸入是...，輸出是...，
有什麼限制條件？時間複雜度有要求嗎？」

2. 暴力解先說（30 秒）：
「最直觀的暴力解是 O(n²)，先說一下思路，
然後我們看能不能優化。」

3. 優化思路（3-5 分鐘）：
「用 [哈希表/雙指針/滑動視窗] 可以優化到 O(n)，
原理是...」

4. 寫代碼（10-15 分鐘）：
邊寫邊說出思路，不要沉默。

5. 驗證（3-5 分鐘）：
「讓我用這個例子走一遍：[trace through]
邊界條件：空輸入、單元素...」
```

### 模塊二：計算機基礎（校招必考）

這是校招的獨特考點，社招很少深問：

#### 操作系統

```
高頻考點：
1. 進程 vs 線程（定義、差異、切換開銷）
2. 死鎖（必要條件、預防、死鎖檢測）
3. 虛擬內存（分頁、TLB、Page Fault）
4. 調度算法（FCFS、SJF、Round Robin、優先級）
5. 文件系統（inode、磁盤調度）

記憶技巧：
死鎖四個必要條件 = 「互不搶循」
互斥（Mutual Exclusion）
不可搶占（No Preemption）
佔有並等待（Hold and Wait）
循環等待（Circular Wait）
```

#### 計算機網絡

```
高頻考點：
1. TCP vs UDP（差異、適用場景）
2. TCP 三次握手（為什麼是三次，不是兩次）
3. TCP 四次揮手（TIME_WAIT 的作用）
4. HTTP vs HTTPS（TLS 握手過程）
5. HTTP/1.1 vs HTTP/2 vs HTTP/3
6. DNS 解析過程
7. 跨域問題（CORS）

深度問題準備：
Q：為什麼 TCP 建立連接要三次握手？
A：「防止已失效的連接請求突然到達服務器而造成錯誤。
   如果只有兩次握手，服務器看到 SYN 就開辟資源，
   但客戶端可能已經不知道了（超時的舊請求），
   這樣服務器的資源被白白消耗。」
```

#### 資料庫基礎

```
高頻考點：
1. 索引（B+ Tree、聯合索引最左前綴、索引下推）
2. 事務四個特性（ACID）+ 隔離級別
3. MySQL vs Redis（什麼場景用什麼）
4. SQL 基礎（JOIN 類型、GROUP BY、HAVING）

深度問題：
Q：B+ Tree 為什麼比 B Tree 更適合資料庫索引？
A：「B+ Tree 所有數據都存在葉子節點，
   內部節點只存鍵值，所以同樣的頁（Page）大小
   能存更多的鍵，樹的高度更低，I/O 次數更少。
   而且葉子節點通過鏈表連接，範圍查詢非常高效。」
```

### 模塊三：系統設計輕量版（校招也開始考）

校招系統設計不需要像社招那樣深，但要展示「有這個思維框架」：

```
基礎框架（每道系統設計題都用）：

Step 1：釐清需求（2-3 分鐘）
「這個系統有多少用戶？QPS 大概多少？
需要支持哪些核心功能？有沒有特殊的可靠性要求？」

Step 2：高層架構（3-5 分鐘）
「大概的架構是：用戶 → 負載均衡 → 應用服務器 → 資料庫
我們需要 [緩存/消息隊列/CDN] 因為...」

Step 3：核心設計（5-10 分鐘）
「最關鍵的問題是 [X]，我的解法是 [Y]，
選擇 Y 而不是 Z 的原因是 [取捨]。」

Step 4：潛在問題（2-3 分鐘）
「這個設計的瓶頸是 [X]，
如果規模繼續增長，可以考慮 [水平擴展/分庫分表/多機房]」
```

## 面試心態：自信不是裝出來的，是準備出來的

極海Channel 觀察到「吊打面試官」的候選人有一個共同點：

```
他們知道自己知道什麼，也知道自己不知道什麼。

問到他們準備好的題：流暢、自信、有深度
問到他們沒準備的題：「這個我不是很熟悉，
                      我從已知的原理來推測一下：
                      [展示工程直覺]
                      我的猜測對嗎？」
```

**誠實地展示邊界，比假裝什麼都會更有說服力。**

## 12 週備戰校招計畫

```
Week 1-4：算法基礎
- 每天 2-3 題 LeetCode Easy/Medium
- 同時複習操作系統基礎（推薦：《現代操作系統》前 5 章）

Week 5-8：算法中階 + 網絡基礎
- 每天 2 題 LeetCode Medium
- 計算機網絡複習（《計算機網絡：自頂向下方法》前 4 章）

Week 9-10：算法高頻 + 資料庫基礎
- 每天 1 題 LeetCode Hard + 3 題 High-frequency Medium
- MySQL 索引、事務、鎖深入學習

Week 11-12：模擬面試 + 系統設計
- 每天 1 場模擬面試（找朋友練或用 Pramp）
- 設計 3-5 個常見系統（短網址、社交 Feed、搶票系統）
- 整理自己的「故事庫」（2-3 個有意義的項目經歷）
```
