# 系統設計現場白板執行技巧

## 為何白板技巧比知識更重要

系統設計沒有唯一正確答案，面試官在評估的是：
1. **溝通能力**：能否清晰傳達思路
2. **結構化思維**：面對模糊問題能否系統拆解
3. **Trade-off 意識**：是否知道每個決策的代價
4. **協作姿態**：是否把面試官當協作者而非考官

---

## 45 分鐘時間分配

```
0:00–0:05  需求釐清（Requirements Clarification）
0:05–0:10  估算規模（Back-of-Envelope Estimation）
0:10–0:15  API 設計（API Design）
0:15–0:25  高層架構（High-Level Design）
0:25–0:40  深度探討（Deep Dive）— 由面試官引導
0:40–0:45  結尾討論（Trade-offs / 未來擴展）
```

嚴格守時是展示「工程紀律」的機會。

---

## 每個階段的執行技巧

### 1. 需求釐清（最重要的 5 分鐘）

**萬用問題清單**：

```
功能範疇：
- 核心功能是哪三個？（不要假設）
- 有哪些功能超出範圍？
- 使用者是誰？（C 端消費者 vs B 端企業 vs 工程師）

規模：
- 多少 DAU / MAU？
- 讀寫比例大概是？
- 是否要求強一致性，還是最終一致性就夠？
- 需要多高的可用性（99.9% vs 99.99%）？

限制：
- 有延遲要求嗎？（P99 < 100ms？）
- 要支援多語系 / 多地區嗎？
- 有特殊法規要求嗎（GDPR 等）？
```

**溝通技巧**：說完假設就確認，不要悶頭設計

```
「我假設 DAU 約 1000 萬，讀寫比是 100:1，
 這樣理解對嗎？」（停，等面試官確認）
```

### 2. 估算規模

用口頭邊算邊說，展示推理過程比結果更重要：

```
「DAU 1000 萬，假設每人每天平均發 10 則貼文
 → 100M 貼文/天 → 約 1000 QPS

 高峰期通常 2–3 倍平均值 → 2000–3000 QPS
 我們設計容量到 5000 QPS（加 buffer）

 每則貼文 1KB 平均 → 100MB/天 → 約 36GB/年
 加上圖片... 另外算」
```

### 3. API 設計

先定 API 再畫架構，展示「由外到內」思考：

```
# 貼文相關
POST   /posts              { content, media_ids[] }
GET    /posts/{post_id}
GET    /users/{user_id}/feed   ?cursor=xxx&limit=20
POST   /posts/{post_id}/likes
DELETE /posts/{post_id}/likes

# 注意：
# - 用 cursor pagination 不用 offset（避免漂移）
# - 冪等設計（重複 like 不報錯）
```

### 4. 高層架構（核心環節）

**白板書寫順序**：
1. 畫 Client → Load Balancer → API Server
2. 加資料庫（先 SQL，討論後再決定是否換 NoSQL）
3. 加快取層
4. 加訊息佇列（如果有非同步需求）
5. 標注數字（QPS、資料量）

**邊畫邊說**：
```
「這裡我放一個 API Server 集群，前面用 Load Balancer 分流。
 資料庫先用 PostgreSQL，因為貼文有關係型結構，
 先不過早優化。快取層用 Redis 放 hot posts...」
```

### 5. 深度探討（被面試官引導）

面試官會 zoom in 某個模組，常見方向：

**「如果 DB 成為瓶頸，怎麼辦？」**
```
1. Read Replica（讀寫分離）
2. Database Sharding（User ID 分片）
3. Cache 擋讀（Redis Cluster）
4. CDN 擋靜態內容
```

**「如何處理熱點用戶（明星）的 Fan-out？」**
```
Push vs Pull 模型：
- 普通用戶：寫入時 push 到所有 follower 的 feed
- 明星用戶（1000萬 follower）：pull 模式，讀取時動態拉取
- 混合模式：follower < 10萬 → push；> 10萬 → pull
```

## 溝通技巧詳解

### Trade-off 表達公式

```
「方案 A 的好處是 [X]，但代價是 [Y]。
 方案 B 解決了 [Y]，但引入了 [Z]。
 鑒於我們的需求是 [需求]，我會選擇 [方案]，因為 [理由]。」
```

範例：
```
「用 Redis 做 Feed Cache，好處是讀取 P99 < 1ms，
 但代價是 Cache Invalidation 複雜度增加，
 以及如果快取失效所有請求打到 DB 可能過載。
 鑒於我們是讀多寫少的場景，快取命中率應該很高，
 我選擇用 Redis，並加 singleflight 防止 cache miss 雪崩。」
```

### 遇到不知道的問題

```
❌ 「我不確定... 可能是 XXX 吧...」（沒信心）
❌ 沉默、跳過

✅ 「這個我沒有深入研究過，但我的思路是這樣...
   你能告訴我這裡的最佳實踐嗎？」
   （誠實 + 展示思維 + 把面試官拉成協作者）
```

### 如何主動引導深度

```
「我剛剛簡單介紹了整體架構。
 您希望我深入哪個部分？
 我覺得 [Feed 生成] 和 [通知系統] 是最有趣的挑戰。」
```

## 白板/線上面試技巧

### 實體白板

- 字寫大一點，確保面試官看得到
- 用不同顏色標記不同層（藍色=服務，綠色=資料庫，紅色=關鍵路徑）
- 留空白：別把白板寫滿，保留修改空間
- 邊寫邊口述，不要悶頭畫圖

### 線上（Miro / Excalidraw / 手繪工具）

- 先問面試官用什麼工具
- 用 Box + Arrow 即可，不需要漂亮
- 標注組件名稱（避免「這個框框」這種說法）
- 截圖存下來，方便最後討論

### 純文字面試（只有 Google Doc）

```
Architecture:
Client → CDN → API Gateway → [User Service, Post Service, Feed Service]
                                     ↓              ↓             ↓
                               PostgreSQL      PostgreSQL      Redis Cluster
                                                 (posts)       (feed cache)
                                                    ↓
                                              Kafka → Worker → Fan-out
```

## 常見地雷

| 地雷 | 正確做法 |
|------|---------|
| 沒問需求就開始設計 | 花 5 分鐘釐清，再動筆 |
| 過早優化（一開始就 Kafka+微服務） | 先 simple，再 scale |
| 只說 what 不說 why | 每個決策說出 trade-off |
| 對面試官提問不耐煩 | 面試官提問是引導，不是挑剔 |
| 時間到了還在畫細節 | 主動說「還有 5 分鐘，我先總結 trade-off」 |
| 不主動說數字 | 估算要有數字，哪怕是粗估 |

## 結尾總結模板

```
「時間差不多了，讓我快速總結：
 核心架構是 [XXX]，
 主要 trade-off 是 [A vs B]，我選了 A 因為 [理由]。
 若要進一步 scale，下一步我會考慮 [XXX]。
 整體設計還有哪裡您想深入討論？」
```
