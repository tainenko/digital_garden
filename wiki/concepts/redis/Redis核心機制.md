# Redis 核心機制

Redis 面試高頻：為何快、單執行緒、過期/淘汰策略、持久化、快取一致性。

## 為何 Redis 快？為何單執行緒？
- **基於記憶體**：讀寫直接走記憶體，速度遠勝磁碟。
- **單執行緒**：免去執行緒上下文切換與**鎖競爭**的開銷，邏輯簡單、無資料競爭。
- **I/O 多路復用（epoll）**：單執行緒即可處理大量併發連線。
- **瓶頸不在 CPU 而在記憶體頻寬與網路**，因此單執行緒已足夠快——這是其單執行緒設計的核心理由。
> 註：Redis 6.x 後網路 I/O 引入多執行緒，但**命令執行仍是單執行緒**。

## 五大基礎資料結構
String、Hash（map）、List、Set、Sorted Set（zset）。

## 過期刪除策略（兩者組合）
- **惰性刪除**：存取 key 時才檢查是否過期 → 省 CPU，但過期 key 可能堆積佔記憶體。
- **定期刪除**：每隔一段時間隨機抽查並刪除過期 key → 折衷 CPU 與記憶體。
- Redis 實際採用**惰性 + 定期**組合。

## 記憶體淘汰策略（maxmemory-policy）
記憶體達上限時的淘汰規則：
- `noeviction`：不淘汰，寫入直接報錯（預設）。
- `allkeys-lru`：對**所有** key 淘汰最近最少使用者（**最常用**）。
- `volatile-lru`：僅對**設了過期時間**的 key 做 LRU。
- `allkeys-random` / `volatile-random`：隨機淘汰。
- `volatile-ttl`：優先淘汰最快過期的 key。
- （新版另有 `allkeys-lfu` / `volatile-lfu`：依存取頻率）

## 持久化：RDB vs AOF
- **RDB**：定時生成記憶體快照；檔案小、恢復快；但兩次快照間當機會丟資料。
- **AOF**：記錄每個寫命令的 append-only log；持久性更好（可逐秒/每命令 fsync）；檔案大、恢復較慢。
- 實務常**兩者並用**，恢復時優先讀 AOF。

## 快取與資料庫一致性
- 推薦 **Cache Aside（旁路快取）**：讀時 miss 則回填快取；寫時**先更新資料庫，再刪除快取**。
- 刪快取（而非更新快取）可避免併發寫入造成的髒資料。
- 仍可能因「刪快取失敗」或讀寫請求穿插造成短暫不一致，屬**最終一致性**；可用延遲雙刪、訊息佇列重試補強。
