# 微服務架構設計原則

## 什麼是微服務

微服務是將單一應用拆分為一組小型、獨立部署的服務，每個服務：
- 圍繞業務能力（business capability）組織，而非技術分層
- 有自己的資料儲存（database per service）
- 透過輕量協議（REST / gRPC / 訊息佇列）通訊
- 可以獨立部署、擴展、失敗

## 單體 vs 微服務的決策

| 面向 | 單體 | 微服務 |
|------|------|--------|
| 開發初期速度 | 快（無網路邊界） | 慢（需要基礎設施） |
| 擴展性 | 整體擴展 | 按需擴展個別服務 |
| 故障隔離 | 無（一個 bug 可以拖垮全服務）| 有（Circuit Breaker 隔離） |
| 部署複雜度 | 低 | 高（需要 K8s / 服務發現 / 分散式追蹤）|
| 適合規模 | 初創、< 5 人工程團隊 | > 5 人，明確的組織邊界 |

**原則**：從單體開始，等邊界清晰再拆。過早微服務是「分散式單體」的噩夢。

## Domain-Driven Design（DDD）劃分服務邊界

微服務的邊界應該沿著 **Bounded Context** 切：

```
電商系統

┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  商品服務     │   │  訂單服務     │   │  用戶服務     │
│  (Catalog)   │   │  (Order)     │   │  (Identity)  │
│              │   │              │   │              │
│  Product     │   │  Order       │   │  User        │
│  Category    │   │  OrderItem   │   │  Address     │
│  Inventory   │   │  Payment     │   │  Auth        │
└──────────────┘   └──────────────┘   └──────────────┘
       │                  │                  │
       └──────────────────┴──────────────────┘
                     Event Bus（Kafka）
```

### 錯誤的邊界劃分（技術分層）

```
❌ 不要這樣
┌───────────┐   ┌───────────┐   ┌───────────┐
│ Controller│   │  Service  │   │    DAO    │
└───────────┘   └───────────┘   └───────────┘
這只是把一個三層架構拆成三個服務，問題反而更多
```

## 12-Factor App

微服務遵循 12-Factor 原則：

| Factor | 原則 | Go 實踐 |
|--------|------|---------|
| 1. Codebase | 一個服務一個 repo | monorepo 或 multi-repo |
| 2. Dependencies | 明確宣告相依 | go.mod |
| 3. Config | 環境變數，不進 code | os.Getenv / Viper |
| 4. Backing services | 把 DB/Redis 當可替換資源 | 介面抽象 |
| 5. Build/Release/Run | 三階段分離 | Dockerfile multi-stage |
| 6. Processes | 無狀態，state 在外部儲存 | 不用 global state |
| 7. Port binding | 服務自行 listen port | http.ListenAndServe |
| 8. Concurrency | 用 process 水平擴展 | K8s replica |
| 9. Disposability | 快速啟動、優雅關機 | signal handler |
| 10. Dev/Prod parity | 開發和生產環境一致 | Docker Compose local |
| 11. Logs | 輸出到 stdout，不管 rotation | zerolog / zap |
| 12. Admin processes | 一次性任務用同一個 image | `cmd/migrate/` |

## 核心設計模式

### Database per Service

每個服務有自己的資料庫，不共用：

```
✅ 正確
訂單服務 → PostgreSQL（訂單相關）
商品服務 → PostgreSQL（商品目錄）
搜尋服務 → Elasticsearch（搜尋索引）
session 服務 → Redis（session）

❌ 錯誤
所有服務 → 同一個 PostgreSQL（服務間通過 DB join 耦合）
```

**好處**：服務可以選最適合的資料庫；一個 DB 故障不影響其他服務

**代價**：跨服務查詢需要 API 呼叫或事件；事務邊界消失（需要 [[Saga Pattern分散式事務]]）

### API Gateway 模式

```
用戶 → API Gateway → 商品服務
                   → 訂單服務
                   → 用戶服務
```

API Gateway 負責：認證/授權、速率限制、請求路由、協議轉換（REST → gRPC）、日誌

### BFF（Backend for Frontend）

不同客戶端（Web / Mobile / 第三方）有不同的 BFF：

```
Web Browser → BFF-Web → [內部服務]
Mobile App  → BFF-Mobile → [內部服務]（回傳更精簡的資料）
```

## 服務間通訊策略

| 方式 | 適用場景 | Go 套件 |
|------|---------|---------|
| REST / HTTP | 簡單查詢，外部 API | net/http, gin, echo |
| gRPC | 高效能內部呼叫，需要 streaming | google.golang.org/grpc |
| Kafka / NATS | 非同步事件、解耦 | confluent-kafka-go, nats.go |
| GraphQL | 需要彈性查詢的 BFF 層 | gqlgen |

**選型原則**：
- 需要即時回應 → gRPC（內部）/ REST（外部）
- 不需要即時回應、可以重試 → 訊息佇列
- 混合：讀用 gRPC，寫用事件

## 分散式系統必學的 CAP 定理

在網路分區（P）時必須在一致性（C）和可用性（A）選一個：
- 選 CP（如 ZooKeeper）：分區時拒絕服務，確保一致性
- 選 AP（如 Cassandra）：分區時繼續提供服務，但可能讀到舊資料

**實務**：大多數業務選 AP + eventual consistency（最終一致性），通過事件和補償機制保證資料最終正確。
