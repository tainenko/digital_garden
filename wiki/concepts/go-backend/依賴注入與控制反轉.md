# 依賴注入與控制反轉（DI / IoC）

## 核心概念

### 控制反轉（IoC）

**不由元件自己建立依賴，而是由外部提供**。「控制」指的是「誰決定用哪個實作」。

```go
// ❌ 沒有 IoC：UserService 自己決定用哪個 DB
type UserService struct{}

func (s *UserService) GetUser(id string) (*User, error) {
    db, err := sql.Open("postgres", os.Getenv("DB_URL")) // 硬編碼依賴！
    if err != nil {
        return nil, err
    }
    defer db.Close()
    // ...
}

// ✅ IoC：由呼叫者決定用哪個實作
type UserService struct {
    repo UserRepository // 介面，不是具體型別
}

func NewUserService(repo UserRepository) *UserService {
    return &UserService{repo: repo}
}
```

### 依賴注入（DI）

IoC 的**實作機制**——依賴透過建構子、方法或欄位從外部「注入」。

**DI 的三種方式**：

```go
// 1. Constructor Injection（建構子注入）← 最推薦
type OrderService struct {
    repo    OrderRepository
    pricing PricingService
    logger  Logger
}

func NewOrderService(
    repo OrderRepository,
    pricing PricingService,
    logger Logger,
) *OrderService {
    return &OrderService{
        repo:    repo,
        pricing: pricing,
        logger:  logger,
    }
}

// 2. Method Injection（方法注入）← 適合可選依賴或請求級別依賴
func (s *OrderService) PlaceOrder(ctx context.Context, cmd PlaceOrderCommand, tracer Tracer) error {
    // tracer 是請求級別的，每個請求可能不同
}

// 3. Field Injection（欄位注入）← 不推薦（無法保證初始化，測試麻煩）
type OrderService struct {
    Repo OrderRepository // exported，由框架注入 ← 避免
}
```

**為什麼用建構子注入**：
- 依賴關係明確（看函數簽名就知道需要什麼）
- 物件建立後保證已初始化（不可能有 nil 依賴）
- 容易寫測試（直接傳 mock）

## 為什麼 DI 讓代碼更好

### 可測試性（最重要的理由）

```go
// 定義介面
type UserRepository interface {
    FindByID(ctx context.Context, id string) (*User, error)
    Save(ctx context.Context, user *User) error
}

type EmailSender interface {
    Send(ctx context.Context, to, subject, body string) error
}

type UserService struct {
    repo   UserRepository
    mailer EmailSender
}

// ✅ 測試時注入 mock，不需要真實 DB 或 SMTP
func TestUserService_Register(t *testing.T) {
    mockRepo := &MockUserRepository{
        SaveFunc: func(ctx context.Context, user *User) error {
            assert.Equal(t, "alice@example.com", user.Email)
            return nil
        },
    }
    mockMailer := &MockEmailSender{
        SendFunc: func(ctx context.Context, to, subject, body string) error {
            assert.Equal(t, "alice@example.com", to)
            return nil
        },
    }

    svc := NewUserService(mockRepo, mockMailer)
    err := svc.Register(context.Background(), RegisterCommand{
        Email: "alice@example.com",
        Name:  "Alice",
    })
    assert.NoError(t, err)
    assert.True(t, mockRepo.SaveCalled)
    assert.True(t, mockMailer.SendCalled)
}
```

### 關注點分離 + 替換實作

```go
// 開發環境：用記憶體 Repository
type InMemoryUserRepo struct {
    mu    sync.RWMutex
    users map[string]*User
}

// 生產環境：用 PostgreSQL
type PostgresUserRepo struct {
    db *sql.DB
}

// 兩者都實作同一個介面，切換只需在 Wire/main 中改一行
// UserService 完全不需要改動
```

## 手動 DI（不用框架）

理解手動 DI 是理解 Wire 的基礎：

```go
// main.go：手動組裝所有依賴（俗稱 Composition Root）
func main() {
    // 1. Infrastructure Layer
    db, err := sql.Open("pgx", cfg.DatabaseURL)
    if err != nil {
        log.Fatal(err)
    }
    defer db.Close()

    redisClient := redis.NewClient(&redis.Options{Addr: cfg.RedisAddr})
    defer redisClient.Close()

    eventBus := kafka.NewEventBus(cfg.KafkaBrokers)

    // 2. Repository（Infrastructure → Domain interface）
    userRepo := postgres.NewUserRepository(db)
    orderRepo := postgres.NewOrderRepository(db, eventBus)
    productRepo := postgres.NewProductRepository(db, redisClient)

    // 3. Domain Service
    pricingService := domain.NewPricingService(productRepo)

    // 4. Application Service
    userSvc := application.NewUserService(userRepo, email.NewSMTPSender(cfg.SMTP))
    orderSvc := application.NewOrderService(orderRepo, productRepo, pricingService)

    // 5. HTTP Handler
    userHandler := http.NewUserHandler(userSvc)
    orderHandler := http.NewOrderHandler(orderSvc)

    // 6. HTTP Server
    router := setupRouter(userHandler, orderHandler)
    server := &http.Server{Addr: cfg.Port, Handler: router}
    server.ListenAndServe()
}
```

**問題**：隨著服務增長，main.go 變成幾百行的「dependency spaghetti」，且每次新增依賴都要手動修改初始化順序。

→ Wire 解決這個問題。

## DI 的 SOLID 連結

DI 是實踐 **D**（Dependency Inversion Principle）的具體手段：

```
SOLID 中的 D：
「高層模組不應依賴低層模組，兩者都應依賴抽象」

Application Service（高層）
    ↓ 依賴
OrderRepository interface（抽象）
    ↑ 實作
PostgresOrderRepository（低層）

修改資料庫 → 只改 PostgresOrderRepository，Application Service 不變
```

**介面設計原則（配合 DI）**：

```go
// ✅ 介面應該盡量小（Interface Segregation Principle）
type OrderReader interface {
    FindByID(ctx context.Context, id OrderID) (*Order, error)
}

type OrderWriter interface {
    Save(ctx context.Context, order *Order) error
}

type OrderRepository interface {
    OrderReader
    OrderWriter
}

// 只需要讀取的服務只依賴 OrderReader
type OrderReportService struct {
    reader OrderReader // 不需要寫入能力
}

// 這讓測試更簡單（mock 更小）
```

## 生命週期管理

DI 中一個重要問題：**物件的生命週期**。

```go
// 三種常見生命週期：

// 1. Singleton（整個應用只有一個實例）
//    適合：DB connection pool、config、Redis client
var dbPool *sql.DB // 一個 pool，被所有 repository 共用

// 2. Scoped（每個請求一個實例）
//    適合：資料庫事務、request context 相關的物件
type RequestContext struct {
    tx  *sql.Tx
    // ...
}

// 3. Transient（每次注入都是新實例）
//    適合：無狀態的 helper、builder

// Wire 的預設行為：每個 Provider 調用一次 → 類似 Transient
// 要 Singleton：在 Provider 外部管理（或用 fx）
```

## 常見反模式

```go
// ❌ Service Locator 反模式（全域容器，依賴隱式）
var container = di.NewContainer()
container.Register("userRepo", NewPostgresUserRepo)

func (s *UserService) DoSomething() {
    repo := container.Get("userRepo").(UserRepository) // 依賴隱藏！
}

// ❌ 在 Struct 中初始化依賴（打破 IoC）
type UserService struct{}
func (s *UserService) GetUser(id string) (*User, error) {
    repo := NewPostgresUserRepo(getDB()) // 自己建立依賴
    return repo.FindByID(context.Background(), id)
}

// ❌ 過度注入（God Object）
type AppService struct {
    // 15 個依賴 → 說明這個 Service 承擔了太多職責
    repo1, repo2, repo3, repo4, repo5 ...
    svc1, svc2, svc3, svc4, svc5 ...
    // 應該拆分成多個 Service
}

// ✅ 正確：依賴少、職責單一
type OrderPlacementService struct {
    orderRepo  OrderRepository
    pricing    PricingService
    inventory  InventoryChecker
}
```
