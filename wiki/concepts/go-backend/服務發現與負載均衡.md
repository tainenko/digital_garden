# 服務發現與負載均衡

## 為什麼需要服務發現

在微服務環境，服務的 IP 和 Port 是動態的（容器重啟、自動擴縮容），不能寫死在設定檔裡：

```
❌ 寫死：payment-service → http://192.168.1.5:8080
   → 容器重啟後 IP 變了，服務掛掉

✅ 服務發現：payment-service → 查詢 "payment-service" 的當前實例清單
                               → 從中選一個健康的
```

## 兩種服務發現模式

### Client-Side Discovery

Client 自己查詢服務登記表，自己做負載均衡：

```
Client → Service Registry（Consul / etcd）→ 取得實例清單
Client → 自己選一個（Round Robin / Random / 最少連線）→ 直接呼叫
```

**優點**：簡單，少一層網路跳轉
**缺點**：每個 Client 都要實作負載均衡邏輯

### Server-Side Discovery（K8s 預設）

Load Balancer 或 Service Proxy 負責查詢和選擇：

```
Client → LB / Service Proxy（Nginx / Istio / K8s Service）→ 選一個後端 → 轉發
```

**優點**：Client 不需要知道服務發現邏輯
**缺點**：多一層跳轉，LB 是潛在單點

## Kubernetes 服務發現（最常用）

K8s 提供內建服務發現，不需要額外的 Consul：

```yaml
# payment-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-service
  namespace: default
spec:
  selector:
    app: payment
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP  # 只能內部訪問
```

```go
// Go 服務直接用 K8s Service DNS 名稱呼叫
// payment-service.default.svc.cluster.local
// 簡寫：payment-service（同 namespace）
paymentClient, err := grpc.NewClient("payment-service:80", ...)
```

K8s 的 kube-proxy 自動做 iptables 規則，把流量分發到各個 Pod（Round Robin）。

## Consul 服務發現

在 K8s 之外（VM 環境、多雲）常用 Consul：

```go
import "github.com/hashicorp/consul/api"

// 服務啟動時註冊
func registerService(client *api.Client, name, host string, port int) error {
    return client.Agent().ServiceRegister(&api.AgentServiceRegistration{
        ID:      fmt.Sprintf("%s-%s-%d", name, host, port),
        Name:    name,
        Address: host,
        Port:    port,
        Check: &api.AgentServiceCheck{
            HTTP:                           fmt.Sprintf("http://%s:%d/health", host, port),
            Interval:                       "10s",
            Timeout:                        "2s",
            DeregisterCriticalServiceAfter: "30s", // 不健康 30s 後自動注銷
        },
    })
}

// 服務關閉時注銷
func deregisterService(client *api.Client, serviceID string) error {
    return client.Agent().ServiceDeregister(serviceID)
}

// Client 查詢服務
func discoverService(client *api.Client, name string) ([]*api.ServiceEntry, error) {
    entries, _, err := client.Health().Service(name, "", true, nil) // 只取健康的實例
    return entries, err
}
```

## 負載均衡策略

### Round Robin（輪詢，最簡單）

```go
type RoundRobinBalancer struct {
    mu       sync.Mutex
    backends []string
    counter  uint64
}

func (b *RoundRobinBalancer) Next() string {
    count := atomic.AddUint64(&b.counter, 1)
    return b.backends[count%uint64(len(b.backends))]
}
```

### Weighted Round Robin（加權輪詢）

```go
// 效能好的機器給更高的 weight
type WeightedBackend struct {
    Address       string
    Weight        int
    CurrentWeight int // 動態計算用
}

func (b *WeightedBalancer) Next() string {
    b.mu.Lock()
    defer b.mu.Unlock()

    // Nginx 的 Smooth Weighted Round Robin 算法
    totalWeight := 0
    var selected *WeightedBackend

    for i := range b.backends {
        b.backends[i].CurrentWeight += b.backends[i].Weight
        totalWeight += b.backends[i].Weight
        if selected == nil || b.backends[i].CurrentWeight > selected.CurrentWeight {
            selected = &b.backends[i]
        }
    }

    selected.CurrentWeight -= totalWeight
    return selected.Address
}
```

### Least Connections（最少連線）

```go
type LeastConnBalancer struct {
    mu       sync.RWMutex
    backends map[string]*atomic.Int64 // address → active connections
}

func (b *LeastConnBalancer) Next() string {
    b.mu.RLock()
    defer b.mu.RUnlock()

    var minAddr string
    var minConn int64 = math.MaxInt64
    for addr, conn := range b.backends {
        if c := conn.Load(); c < minConn {
            minConn = c
            minAddr = addr
        }
    }
    b.backends[minAddr].Add(1)
    return minAddr
}

func (b *LeastConnBalancer) Done(addr string) {
    b.backends[addr].Add(-1)
}
```

### Consistent Hashing（一致性雜湊）

適合需要「同一個 key 總是打到同一個服務」的場景（如分散式快取路由）：

```go
import "github.com/serialx/hashring"

ring := hashring.New([]string{"node1:6379", "node2:6379", "node3:6379"})

// 同一個 key 永遠路由到同一個 node
node, _ := ring.GetNode("user-123")

// 新增節點時，只有少部分 key 需要重新路由
ring.AddNode("node4:6379")
```

## 健康檢查整合

負載均衡器必須只把流量發給健康的實例：

```go
type HealthAwareBalancer struct {
    mu       sync.RWMutex
    all      []string
    healthy  map[string]bool
}

// 背景 goroutine 定期健康檢查
func (b *HealthAwareBalancer) StartHealthCheck(ctx context.Context, interval time.Duration) {
    ticker := time.NewTicker(interval)
    go func() {
        for {
            select {
            case <-ctx.Done():
                return
            case <-ticker.C:
                for _, addr := range b.all {
                    healthy := b.checkHealth(addr)
                    b.mu.Lock()
                    b.healthy[addr] = healthy
                    b.mu.Unlock()
                }
            }
        }
    }()
}

func (b *HealthAwareBalancer) checkHealth(addr string) bool {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()
    req, _ := http.NewRequestWithContext(ctx, "GET", "http://"+addr+"/health", nil)
    resp, err := http.DefaultClient.Do(req)
    return err == nil && resp.StatusCode == 200
}

func (b *HealthAwareBalancer) Healthy() []string {
    b.mu.RLock()
    defer b.mu.RUnlock()
    var result []string
    for addr, ok := range b.healthy {
        if ok {
            result = append(result, addr)
        }
    }
    return result
}
```

## Service Mesh（Istio / Linkerd）

在 K8s 環境，Service Mesh 把服務發現、負載均衡、mTLS、追蹤全部下沉到 sidecar proxy（Envoy），Application code 完全不需要感知：

```
┌─────────────────────────────────┐
│  Pod                            │
│  ┌─────────────┐  ┌──────────┐  │
│  │ App（Go）   │  │  Envoy   │  │  ← sidecar，攔截所有流量
│  │             │→ │  Proxy   │  │
│  └─────────────┘  └──────────┘  │
└─────────────────────────────────┘
```

Istio 提供：
- 自動 mTLS（服務間加密）
- 流量管理（金絲雀發布、A/B 測試）
- 可觀測性（自動產生 traces、metrics）

**代價**：複雜度高，Envoy sidecar 增加 latency（通常 < 1ms）和資源消耗。
