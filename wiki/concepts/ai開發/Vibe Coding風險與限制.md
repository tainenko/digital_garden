# Vibe Coding 風險與限制

Vibe Coding 帶來速度，但也引入可量化的風險。理解這些限制，才能在正確的場景使用它。

## 程式碼品質問題

| 問題 | 數據 | 來源 |
|------|------|------|
| 重大缺陷比人寫多 | **1.7 倍** | 470 個 GitHub PR 分析 |
| 安全漏洞比人寫多 | **2.74 倍** | 同上 |
| 可讀性問題 | **3 倍** 更多 | 同上（增幅最大的單一問題） |
| AI 生成含安全漏洞比例 | 約 **45%** | abmedia 2026 報告 |
| 程式碼重複增加 | **4 倍**（2021→2024）| Wikipedia |
| 程式碼重構比例下降 | 25% → 10% | Wikipedia |

## 安全風險

- AI 訓練資料含有大量過時或不安全的編程慣例
- 可能引入已被棄用（deprecated）的套件
- 「幻覺套件」：AI 虛構一個不存在的套件名稱，若被惡意人士搶先註冊，將藏入惡意程式碼
- **嚴重案例**：2025 年 Lovable 平台——1,645 個生成 web app 中有 **170 個**暴露個人資料漏洞

## 技術債累積

- AI 傾向實作功能，但不考慮架構優雅性與可維護性
- 「一個人的 Vibe Coding 可能變成 100 個人的技術債」
- 缺乏測試覆蓋、文件、模組化設計

## 認知風險

- **理解空洞**：開發者不了解自己的系統，當 AI 失效時無法排除問題
- **技能退化**：新進開發者可能從未建立對程式語言的深層理解
- **工具依賴**：對特定平台的過度依賴（vendor lock-in）

## 效率的反直覺數據

METR 2025 年 7 月研究：**有經驗**的開源開發者使用 AI 工具後反而慢了 **19%**，但他們事前預測自己會快 24%。原因：AI 在簡單任務快，但複雜多檔案任務反而增加認知負擔。

## 降低風險的實踐方式

1. **安全敏感系統強制 code review**：不論 AI 生成速度多快
2. **不把 AI 輸出當答案**：當起點，需人工驗證
3. **逐步接受修改**：不要一次 accept 大量 diff
4. **保持理解**：定期閱讀 AI 生成的程式碼，不完全信任

## 技術工程師 vs 非技術用戶的風險差異

[[Erik Schluntz]]（Anthropic）指出：媒體報導的安全漏洞多來自完全不懂程式碼的非技術人員。技術工程師若搭配 TDD 與可驗證抽象層，生產環境風險遠低於媒體渲染。詳見 [[生產環境Vibe Coding四大策略]]。
