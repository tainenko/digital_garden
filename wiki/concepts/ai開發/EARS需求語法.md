# EARS 需求語法（Easy Approach to Requirements Syntax）

EARS 是由 Alistair Mavin 與 Rolls-Royce 團隊於 2009 年提出的需求描述語法，後被 Airbus、NASA、Siemens 等採用。核心目標：**將模糊的形容詞轉化為精準的指令**，讓需求不再被「合理解讀」出不同版本。

在 AI 輔助開發中，EARS 格式能大幅降低 AI 的猜測空間，是 SDD 規格寫作的基礎語法工具之一。

---

## 五種句型

| 類型 | 結構 | 用途 |
|------|------|------|
| **Ubiquitous（通用型）** | `系統必須 [行為]` | 永遠成立的規則，無條件觸發 |
| **Event-driven（事件驅動型）** | `當 [事件發生] 時，系統必須 [行為]` | 特定事件觸發的行為 |
| **Unwanted Behavior（異常處理型）** | `如果 [異常條件]，系統必須 [行為]` | 錯誤、邊界條件的處理方式 |
| **State-driven（狀態驅動型）** | `當處於 [某種狀態] 時，系統必須 [行為]` | 系統在特定狀態下的行為約束 |
| **Optional Feature（選配型）** | `若有 [特殊功能]，系統必須 [行為]` | 只在某功能存在時才適用的規則 |

---

## 電子錢包扣款 API 範例

```
# 事件驅動型
當使用者發起扣款請求時，系統必須驗證帳戶餘額是否充足。

# 異常處理型
如果帳戶餘額不足，系統必須回傳 HTTP 402 並包含當前餘額資訊。

# 狀態驅動型
當帳戶處於凍結狀態時，系統必須拒絕所有扣款請求並回傳 HTTP 403。

# 通用型
系統必須記錄所有扣款嘗試（成功或失敗）至審計日誌。
```

## 為什麼 EARS 對 AI 開發特別重要

| 問題 | 自然語言 prompt | EARS 格式 |
|------|----------------|-----------|
| 邊界條件 | AI 猜測要不要處理 | 異常處理型明確規定 |
| 觸發時機 | AI 自行判斷 | Event-driven 明確指定 |
| 狀態轉換 | AI 可能遺漏 | State-driven 強制聲明 |
| 可測試性 | 不確定怎麼驗證 | 每個句型直接對應測試案例 |

---

## EARS vs 其他需求格式

| 格式 | 特色 | 適合階段 |
|------|------|---------|
| **EARS** | 法律條文式，結構嚴謹，覆蓋異常與狀態 | 需求定義（PM/架構師） |
| **BDD（Given/When/Then）** | 電影劇本式，強調驗收場景，可直接轉測試 | 驗收標準（工程師/QA）|
| **User Story** | 「作為...我希望...」，強調用戶視角 | 需求溝通（PM/PO） |

**最佳組合**：EARS 定義規則 → BDD 定義驗收場景 → User Story 溝通背景。
