# SDD 成熟度三層次

高見龍提出的 SDD 實踐分類框架，描述組織與工具在「規格與程式碼關係」上的三個演進階段。這個框架有助於評估自己當前的 SDD 實踐在哪個層次，以及下一步應往哪裡走。

---

## 三個層次

### Layer 1：Spec-first（規格優先）
**定義**：寫規格後生成程式碼，規格只是起點，事後可丟棄。

**特徵**：
- 規格是一次性的起點文件，不需保持同步
- 程式碼才是真相源（Source of Truth）
- 規格完成後進入正常開發流程，規格可以與程式碼分歧

**代表工具**：GitHub Spec Kit（Constitution 概念）

**適合**：快速啟動新專案、團隊剛開始採用 SDD、規格品質還在建立中

**代價**：規格漂移——規格寫好後需求改了，規格不再反映現實

---

### Layer 2：Spec-anchored（規格錨定）
**定義**：規格納入版本控制，持續更新，是所有變更的基準點。

**特徵**：
- 規格與程式碼共同存活在 repo 中
- 任何功能變更，先改規格，再推導程式碼
- 規格是 PR review 的一部分
- 人類仍然維護程式碼，規格是「決策記錄」

**代表工具**：OpenSpec（specs/changes 分離）、Kiro（Amazon，EARS 格式 + Hooks）

**適合**：多人協作、長期維護的系統、需要合規記錄、需要決策追溯

**代價**：規格維護成本——需要紀律確保規格與程式碼同步

---

### Layer 3：Spec-as-source（規格即來源）
**定義**：程式碼完全由規格自動生成，開發者不直接編輯程式碼。

**特徵**：
- 規格是唯一的真相源，程式碼是副產品
- 程式碼是不可直接修改的生成物
- 任何改動都發生在規格層面
- 需要極高品質的規格才能運作

**代表工具**：Tessl（10,000+ OSS usage specs）

**適合**：規格品質成熟、需求穩定、有足夠的規格測試覆蓋

**代價**：對規格品質要求極高；一旦規格有錯，程式碼全錯；工具生態仍在早期

---

## 三層次對照表

| 面向 | Spec-first | Spec-anchored | Spec-as-source |
|------|-----------|---------------|----------------|
| 規格角色 | 起點文件 | 持續維護的基準 | 唯一真相源 |
| 程式碼角色 | 主要 artifact | 共同 artifact | 自動生成的副產品 |
| 規格壽命 | 可拋棄 | 與程式碼共同演化 | 永久維護 |
| 人類維護 | 程式碼 | 規格 + 程式碼 | 僅規格 |
| 適合規模 | 個人、小團隊 | 中大型團隊 | 規格成熟的組織 |
| 代表工具 | GitHub Spec Kit | OpenSpec、Kiro | Tessl |
| 主要風險 | 規格漂移 | 維護負擔 | 規格品質門檻極高 |

---

## 如何選擇層次

**從 Spec-first 開始**，原因：
- 學習曲線最低
- 可以快速體驗 SDD 的價值
- 不需建立規格同步流程

**升級到 Spec-anchored 的時機**：
- 團隊超過 3 人
- 系統需要長期維護
- 開始遇到「為什麼這樣設計」的問題

**謹慎考慮 Spec-as-source**，直到：
- 組織對規格寫作有成熟實踐（EARS / BDD 標準化）
- 有完整的規格驗證流程
- 工具生態（如 Tessl）已達到生產成熟度
