# SDD 適用邊界

[[Spec驅動開發]]（SDD）不是萬能解法。它在特定情境下能顯著提升 AI 輔助開發品質，但在另一些情境下會帶來比問題更重的 overhead。理解邊界比學習工具本身更重要。

---

## 一句話判斷原則

> **規格有效的條件**：目標清晰且可測量、邊界明確且可驗證、需求在開發期間不會劇烈改變。——William Yeh

反過來說：目標模糊、需求快速演化、探索性質強的任務，SDD 多半弊大於利。

---

## 適合 SDD 的情境

| 情境 | 原因 |
|------|------|
| **0→1 新產品，需求已收斂** | 規格先行防止方向偏差，避免 AI 猜測技術選型 |
| **多人/多團隊協作** | 規格是跨人溝通的共同語言，防止各自理解不同 |
| **企業級合規需求** | 需要可稽核的決策記錄（為什麼選這個資料庫？） |
| **穩定合約與已知領域** | 規格能被完整定義，AI 照規格執行即可 |
| **長期維護的系統** | 規格是知識轉移的載體，防止「為什麼這樣設計」消失 |
| **技術選型實驗** | 先用規格定義評估標準，再做選型決策 |

---

## 不適合 SDD 的情境

### 1. 線上緊急 Hotfix
時間壓力下，維護規格、等待規格審查的 overhead 遠大於直接修程式碼的風險。規格的更新速度永遠跟不上緊急事故的處理速度。

### 2. 純探索性研究 / 一次性腳本
你還不知道「要做什麼」，就無法寫出有意義的規格。此時寫規格等於「寫一份可能全錯的設計文件」，之後要全部重來。

### 3. 個人學習 Demo
工程化開銷超過學習收益。做 Demo 的目的是快速驗證概念，不是建立長期可維護的系統。

### 4. 需求快速演化的早期探索

這是最常被忽略的邊界。**「現實的變化速度快於規格的更新速度」**（Isoform, DEV Community, 2025）。

具體症狀：
- 規格寫好後，需求就改了，三份文件（規格、程式碼、README）開始分歧
- 以帳單系統加入歐盟 VAT 為例：改程式碼比改規格再讓 AI 重新生成更快
- 開發者花大量時間同步規格，而不是在解決真正的問題

### 5. 既有大型 Codebase 的功能迭代

在成熟系統上新增功能時，SDD 的問題特別明顯（Marmelab, 2025）：
- Agent 靠文字搜尋發現 context，容易遺漏需要同步更新的既有功能
- 規格無法全面描述龐大系統的隱性約束與歷史決策
- 收益隨系統規模遞減

---

## SDD 的四大系統性失敗模式

根據多個批評來源的交叉分析：

### 失敗一：規格維護稅（Spec Maintenance Tax）
規格是額外的 artifact，和程式碼、文件形成三角形——任何改動都要同步三者。隨著系統複雜度增加，這個稅率遞增，最終可能讓工程速度減半而非加倍。

**ROI 時間線**：前 1–3 個月 ROI 為負（學習成本 + 工具設置 + 流程改變）；小團隊約 3 個月回到損益平衡，大型企業可能需要 6 個月。

### 失敗二：缺失的隱性 Context
規格只能描述「做什麼」，無法捕捉「為什麼這樣決策」。邊界條件、效能問題、用戶行為這些知識只在**部署後**才浮現，寫再詳細的規格都描述不到。

### 失敗三：虛假的完整感
詳細規格製造「已涵蓋一切」的錯覺，團隊因此減少迭代頻率、降低創意解法的嘗試——使開發變得像瀑布式一樣僵化，只是把「PM 寫規格、工程師實作」換成了「人寫規格、AI 實作」。

### 失敗四：錯誤的抽象層次
現有 SDD 工具（包含 spec-kit）聚焦在實作細節（欄位名稱、schema 結構、API signature），而非意圖與約束。結果是 AI 產出「結構正確但方向偏差」的程式碼——通過規格驗證，卻不是用戶真正需要的。

## SDD ≠ 瀑布？（Thoughtworks 反駁）

Thoughtworks APAC 技術總監 Liu Shangqi 的立場與 Marmelab 正面衝突：

> 「瀑布的問題在於反饋週期太長、設計與實作脫節。SDD 透過短而有效的 AI 輔助迭代引入工程紀律，本質不同。」——Liu Shangqi, Thoughtworks（2025-12）

兩個框架的核心分歧：

| 立場 | 代表 | 論點 |
|------|------|------|
| SDD = AI 版瀑布 | Marmelab CEO（Zaninotto） | 同樣的「大設計前置」邏輯，軟體本質不確定性無法被規劃消除 |
| SDD ≠ 瀑布 | Thoughtworks（Liu Shangqi） | 反饋週期短、AI 輔助迭代，與瀑布的漫長週期本質不同 |

**建議**：兩個觀點都值得參考。區別在於你的 SDD 實踐是「一次性大規格然後交給 AI 執行」（更像瀑布），還是「持續迭代規格並短週期驗證」（更像敏捷）。

## 與瀑布模型的結構性相似

François Zaninotto（Marmelab CEO）的核心批評：SDD 和瀑布模型的邏輯**完全相同**——

> 瀑布：「用詳細文件讓開發者能直接翻譯規格為程式碼」  
> SDD：「用詳細規格讓 AI agent 能直接翻譯需求為程式碼」

兩者都預設「規劃可以消除不確定性」。《沒有銀彈》早已指出：軟體開發的本質複雜性（essential complexity）無法被任何方法論消除。

---

## 規格失效的早期警訊

- 多輪 AI 互動中，前面的決策開始污染後面的判斷
- 無法清楚區分「必要約束」（不能改的）和「實作細節」（AI 可以自決的）
- 規格文件變成超過 500 行的 Markdown，開發者開始跳過不讀
- Agent 在規格上的「通過驗證」，但產出和用戶期待仍有明顯落差

---

## 替代與互補方案

| 替代方案 | 適用情境 | 核心差異 |
|---------|---------|---------|
| **Context Engineering** | 需求快速演化 | 動態維護意圖與約束，而非靜態規格文件 |
| **自然語言開發（NLD）** | 早期探索、個人開發 | 精實創業式迭代：識別假設→最小實驗→驗證→下一輪 |
| **Vibe Coding** | 快速原型、Demo | 完全不寫規格，直接迭代 |
| **SDD + 輕量規格** | 中型功能 | 只寫「驗收標準」不寫架構細節，降低維護稅 |

```
需求穩定性  高 ──────────────────── 低
                │                      │
團隊規模大  ├── SDD 最有價值          │
               │                      │
團隊規模小  ├── 輕量 SDD              ├── NLD / Vibe Coding
               │                      │
探索性強    └── Context Engineering ──┘
```

## 瓶頸轉移視角（William Yeh, 2026）

即使在 SDD 不適用的情況，工程紀律並未消失——它以新形式出現：

- 規格 → **測試作為治理語言**（界定 AI 可動與禁動的範圍）
- 文件 → **程式碼可理解性**（乾淨命名降低 AI 幻覺風險）
- 規劃 → **架構決策記錄**（ADR，記錄「為什麼」而非「怎麼做」）

抽象層持續上升：從「人類讀懂每行程式碼」→「人類理解模組意圖」→「人類掌控架構決策」。
