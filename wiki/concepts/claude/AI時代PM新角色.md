# AI 時代 PM 新角色

來自 [[Cat Wu]]（Anthropic 產品負責人）的第一手觀察：當 AI 把工程成本壓到近乎零，PM 的職責從「跨部門協調者」演變為「產品品味的定義者與 Evals 的建造者」。

> 「隨著代碼編寫成本變得越來越低，決定『寫什麼』變得更有價值。」

---

## 舊 PM vs 新 PM

| 舊 PM（AI 前）| 新 PM（AI 原生）|
|-------------|----------------|
| 撰寫詳盡 PRD | 製作 Evals 定義成功/失敗 |
| 跨季度路線圖協調 | 清障，確保 1 天內可以發布 |
| 管理跨部門依賴 | 建立自助發布流程 |
| 決定構建什麼（based on spec）| 感知模型邊界，定義「黃金路徑」|
| 弄清楚需求再讓工程師動手 | 讓能快落地的先試，快速驗證 |
| 扮演「跨部門膠水」 | 扮演「Claude 的產品經理」|

---

## 最稀缺的技能：產品品味

**產品品味（Product Taste）**是指能感知「什麼是令人愉悅的用戶體驗、什麼是有價值的功能、什麼值得構建」的直覺能力。

Cat Wu 的觀察：
- 這種技能與背景無關（工程師、設計師、PM 都可能有）
- Anthropic 幾乎對任何展現出這種特質的人都願意錄用
- 工程背景的額外優勢：能預判一件事的**難度**，從而做更好的優先級判斷

> 「如果某樣東西構建起來非常容易，與其爭論不休，不如直接花一小時把它做出來。」

## 新核心技能一：製作 Evals（評測集）

### 什麼是 Evals
Evals 是定義「模型表現成功/失敗」的測試案例集合，類似軟體的 unit test，但測試的是 AI 的行為品質。

### 為什麼是 PM 的工作
- Evals 本質上在問：「什麼叫做這個功能運作正確？」
- 這個問題的答案就是 PM 存在的理由
- 工程師可以讓測試通過，但**定義測試是什麼**是 PM 的責任

### 如何製作 Evals
Cat Wu 的方法：
1. 找 5–10 個代表性案例（不需要數百個）
2. 各自定義「成功的輸出」是什麼樣子
3. 找出**最值得信任的反饋人**（少數人能清楚表達模型哪裡好/壞）
4. 用 Evals 量化目標，衡量進展，找出缺口

> 「評估基準是一項被低估的工作。PM 的職責是定義什麼是成功、什麼是失敗，並親自參與 Evals 的製作。」

### 模型反思技巧
當模型出現意外行為時：
```
不要只是修 prompt，先問模型：
「你剛才為什麼這樣做？」

常見原因：
- 系統提示詞中有令人困惑的內容
- 模型沒意識到某個步驟是任務的一部分
- 子 Agent 沒有執行驗證，主 Agent 沒有 check
```

## 新核心技能二：感知模型邊界，定義「黃金路徑」

### 黃金路徑的意義
模型能力強大但有邊界，用戶體驗的好壞取決於 PM 能否：
1. 知道模型在哪些場景下穩定可靠
2. 設計 UX 把用戶引導到這些場景
3. 在模型不穩定的邊界處加護欄或給提示

### 感知能力如何培養
- **大量使用**：親自使用，達到 30% 的工作時間在測試邊界
- **詢問原因**：每次模型出現意外行為，追問它為什麼
- **找可信反饋人**：建立 5 人左右的「模型評估可信小組」
- **看行為數據**：海量數據中提取假設，再找數據驗證

---

## 新核心技能三：清障（Unblocking）

### 速度是 AI 時代 PM 的核心 KPI
不是季度 OKR 完成率，而是：
- 從「想法」到「用戶手中」需要多少天？
- 每個發布環節有沒有不必要的等待？
- 工程師可以在「不被阻塞」的情況下自主發布嗎？

### 清障的實際做法
- 建立預先就定位的跨職能待命流程（[[Anthropic 日級迭代發布機制]]的 Evergreen 機制）
- 明確「什麼時候需要 PM 介入，什麼時候不需要」
- 建立團隊原則清單：每個人都知道核心用戶是誰、為什麼這些取捨是合理的

## 新核心技能四：預判模型能力缺口

> 「為一個月後的模型做產品。」— 快刀青衣 整理 Cat Wu 核心觀點

### 核心邏輯

AI 產品的競爭窗口往往在於：**在模型填補某個能力缺口之前，搶先把產品做好**。

```
現在的模型：準確率 70% → 不夠好，不能直接用
一個月後的模型：準確率 95% → 這個功能突然成立了

如果你等到模型夠好才開始做：別人已經先你兩個月
如果你現在就做：你知道缺的是什麼，模型一升級，你就領先
```

### 實際操作

1. **選定方向，不等完美**：選一個你認為「有潛力但現在模型還不夠好」的功能
2. **找出關鍵缺口**：記錄哪些邊緣案例還做不到，哪些場景會失敗
3. **保持 Evals 就緒**：當新模型出來，立刻跑 Evals，確認缺口是否填補
4. **快速上線**：新模型一上，你的功能馬上可以交付

### Anthropic 自身案例

Claude Code 的 Code Review 功能：
- 在 Opus 4.5/4.6 之前，準確率不足，無法上線
- 但 PM 一直維護著「功能做好了，等模型」的狀態
- 新模型一出，立刻發布，成為領先功能

> 「構建那些目前還不一定能完美運行的產品，這樣你才能明確缺失了什麼；當新模型出現，替換進去就是領先產品。」

## 角色邊界的消失

Anthropic 的工程師、PM、設計師界線正在模糊：

- 工程師直接從 Twitter 看到用戶反饋 → 週末自行做出功能
- PM 直接寫 code 做原型
- 設計師同時做前端工程

Cat Wu 的結論：
> 「我們傾向招聘那些能夠胜任多重角色、能夠靈活切換，並且在做任何有助於團隊推進的工作時都毫無自負心的人。」

**「只管去做」（Just Do It）** 是 Cat Wu 的核心人生格言：
- 理解限制條件 → 用第一性原理推導正確行動
- 跨越職能邊界去解決問題，不等許可
- 帶 bug 發布 → 快速修復，而不是等完美

---

## 什麼是 PM 仍不可替代的？

即使 Claude 能做大部分的工作，人類 PM 仍有優勢的地方：

| 人類優勢 | 說明 |
|---------|------|
| 隱性知識 | 利益相關者關係、組織政治、未成文的規則 |
| 情商 | 知道如何讓不同人保持協作 |
| 常識 | 感知「成千上萬個動態環節」中哪裡可能出錯 |
| 定義 Evals | 決定什麼叫做「成功」 |
| 最終決策 | Claude 提供所有可能性，人類決定「最終包含什麼」|

---

## 给 AI 時代 PM 的建議

1. **每天花 30% 的時間測試你的產品**，找出模型的失敗邊界
2. **把「寫 Evals」當成日常工作**，而不是偶爾才做的工程任務
3. **對模型的意外行為保持強烈好奇心**：追問「為什麼」比修 prompt 更有效
4. **建立自己的 5 人可信反饋群**：找到能清楚表達模型好壞的人
5. **學會跨越邊界行動**：PM / 工程師 / 設計師的界線消失了，誰能做就去做
