# Claude Prompt 工程核心技巧

Prompt 工程是讓 Claude 穩定輸出高品質結果的核心能力。相比通用 LLM 技巧，Claude 有幾個獨特的特性值得掌握。

---

## Claude 的核心特性

1. **注重誠實**：Claude 不會為了迎合你而說謊，適合當「第二意見」
2. **長文本處理強**：200K context window，可以讀整個代碼庫
3. **遵循複雜指令**：能在單一 prompt 中處理多個互相關聯的限制條件
4. **自主行動能力**：Claude Code 模式下可以主動使用工具、迭代改進

---

## 基礎技巧：結構化 Prompt

### 1. 角色 + 任務 + 格式 三段式

```
你是一位資深 Go 後端工程師，熟悉 Clean Architecture 和微服務設計。

任務：
審查以下 UserService 程式碼，找出：
1. 潛在的競態條件
2. 不符合 Go 慣例的寫法
3. 可能的效能問題

輸出格式：
每個問題一個區塊，包含：問題描述、嚴重程度（高/中/低）、修正建議

程式碼：
[貼入程式碼]
```

### 2. 給範例（Few-Shot）

不要只說「寫 Go 風格的錯誤處理」，直接給範例：

```
請照以下風格處理 error：

✅ 正確範例：
func GetUser(ctx context.Context, id int64) (*User, error) {
    user, err := repo.FindByID(ctx, id)
    if err != nil {
        return nil, fmt.Errorf("GetUser: %w", err)
    }
    return user, nil
}

❌ 不要這樣：
func GetUser(ctx context.Context, id int64) (*User, error) {
    user, err := repo.FindByID(ctx, id)
    if err != nil {
        log.Println(err)
        return nil, err
    }
    return user, nil
}

現在請用正確風格重寫以下函數：
[貼入程式碼]
```

### 3. 限制範圍，明確排除

```
只修改 handlers/user.go，不要碰：
- 任何 repository 層的檔案
- models/ 目錄
- go.mod

如果你認為其他地方需要修改，請只列出建議，不要直接修改。
```

## 中階技巧：引導思考過程

### Chain-of-Thought（思維鏈）

讓 Claude 在回答前先思考，能提升複雜問題的準確率：

```
在給我建議之前，請先：
1. 列出你對這段程式碼的所有疑問
2. 描述你的分析思路
3. 評估可能的解法及各自的取捨
4. 最後給出你的建議
```

### 要求 Claude 質疑自己

```
給我一個解決方案，然後扮演一個嚴格的 reviewer 找出它的缺點，
最後根據這些缺點改進你的解決方案。
```

### 先規劃，後執行

大任務分兩步走，避免 Claude 自作主張：

```
步驟一：
先告訴我你打算怎麼做這個重構，列出：
- 哪些檔案會被修改
- 每個檔案改什麼
- 可能的風險點

（等我確認後再開始）
```

確認計畫後再說：「好，請開始執行。」

## 進階技巧：長任務管理

### 給 Claude 一個「任務清單」格式

適合複雜的多步驟任務：

```
請完成以下任務，每完成一項請在前面打 ✅：

[ ] 讀取 internal/user/ 下的所有檔案，理解現有架構
[ ] 找出所有沒有 unit test 的 Service 方法
[ ] 為每個方法寫測試，放在對應的 _test.go 檔案
[ ] 執行 go test ./internal/user/... 確認全部通過
[ ] 回報測試覆蓋率
```

### 設定「停止條件」

避免 Claude 做過頭：

```
如果你遇到以下情況，停下來問我再繼續：
1. 需要修改超過 5 個以上的檔案
2. 涉及到 database schema 變更
3. 發現原始需求可能有矛盾
```

### 明確的驗收標準

```
任務完成後，請確認：
- [ ] go build ./... 沒有錯誤
- [ ] go test ./... 全部通過
- [ ] golangci-lint run 沒有新的 warning
- [ ] 新增的函數都有 JSDoc/godoc 說明
```

## Claude 特有技巧

### 利用 Claude 的誠實性做 Sanity Check

```
我打算用 Redis SETNX 實作分散式鎖，但我懷疑這樣會有問題。
你覺得這個方案有什麼缺陷？請不要為了迎合我而假裝它沒問題。
```

Claude 會直接指出問題（Redlock 的過期時間、網路分區等），而不是附和你。

### 要求替代方案比較

```
給我三個實作這個功能的不同方法，包含：
- 各自的優缺點
- 適合的場景
- 估計的實作時間

我需要你給出你個人的推薦，並說明理由。
```

### 利用 Claude 的長 context 能力

```
請閱讀整個 internal/ 目錄下的所有 Go 檔案，
然後找出：
1. 所有違反 DRY 原則的重複程式碼
2. 所有不一致的命名模式
3. 所有沒有處理的 error

輸出格式：CSV，欄位為：檔案路徑、行號、問題類型、說明
```

## 給 AI「交底」而不是「許願」

來自 Cat Wu 的核心 prompt 理念：**你自己想清楚了什麼，AI 才能給你什麼**。

> 「如果你不知道自己要什麼，就算是最強的 AI 也只能給你一堆正確的廢話。」

### 許願 vs 交底

| 許願式 Prompt | 交底式 Prompt |
|-------------|-------------|
| 「幫我做一個邏輯清晰的 PPT」 | 提供：市場行銷大綱 + Slack 討論記錄 + 現有簡報模板 + 主題演講主題檔案 |
| 「幫我寫一篇好文章」 | 提供：目標受眾、核心論點、三個已知例子、不能踩的地雷 |
| 「幫我改善這段程式碼」 | 提供：效能瓶頸的 profiling 數據、不能動的 API 合約、期望的吞吐量目標 |

### 交底的五個要素

在給 AI 任何複雜任務前，先確認你能提供：

```
1. 背景材料：已有的文件、討論、數據、範例
2. 成功定義：什麼樣的輸出算是「好」？有沒有你可以比對的參考樣本？
3. 限制條件：什麼不能碰、什麼風格要遵循、什麼是死線
4. 決策授權：哪些決定讓 AI 自己做，哪些必須回來問你
5. 迭代計畫：第一步要 3 個方向還是 1 個最佳方案？
```

### 實戰案例：Cat Wu 的 PPT 自動化

**許願版**：「幫我做一個關於 CoWork 的 Anthropic 風格 PPT」

**交底版**：
```
背景材料：
- Anthropic 行銷大綱（Google Drive 連結）
- 過去兩週的 Slack 討論 #cowork-launch
- Anthropic 官方簡報模板（附件）
- 本次主題演講檔案（確認不重疊的主題）

成功定義：
- Anthropic 設計風格，20 頁
- 涵蓋：功能介紹、使用案例、數據亮點
- 不與主題演講的內容重疊

第一步輸出：3 個大綱方向，我選定後再展開
```

**結果**：CoWork 工作 1 小時，輸出設計水準的完整草稿，人類只需一輪反饋。

### 為什麼「交底」比「許願」重要

- AI 的能力在於**在你定義的框架內，做出超越你預期的連結**
- 如果你沒有框架，AI 只能猜測「一般人認為什麼是好的 PPT」
- 你的獨特知識（內部數據、組織背景、個人品味）= 你真正的輸入
- 只有你提供了這些，AI 的輸出才是「你的」而不是「通用的」

## System Prompt vs User Prompt

在 API 使用中，兩者有不同的適用場景：

| | System Prompt | User Prompt |
|--|--------------|-------------|
| 用途 | 持久的角色/規範定義 | 當前任務的具體指令 |
| 優先級 | 高（但 user prompt 可覆蓋） | 動態 |
| 適合放 | 語言、風格、禁止事項 | 具體任務、上下文、資料 |
| 範例 | 「你是一位 Go 工程師...」 | 「請修改這段程式碼...」 |

## 常見 Prompt 反模式

| 反模式 | 問題 | 改法 |
|--------|------|------|
| 「幫我優化這段程式碼」 | 太模糊，Claude 不知道優化什麼 | 「幫我降低這段程式碼的記憶體使用量」 |
| 「用最好的方式實作」 | 「最好」沒有客觀標準 | 「用讀寫性能最佳的方式，可以犧牲記憶體」 |
| 一次問太多問題 | Claude 可能漏掉部分問題 | 分開問，一次一個主題 |
| 沒給上下文就問 bug | Claude 只能靠猜 | 提供錯誤訊息、相關程式碼、重現步驟 |
