# 複利工程思維（Compounding Engineering）

## 概念來源

由 Dan Shipper 提出，[[Boris]] 在 Claude Code 工作流中實踐並推廣。核心洞察：**每一次對 AI 工作流的小改善都會自動累積**，如同複利一樣在未來每個 session 中生效，而不是一次性的效率提升。

## 核心機制

```
一個問題出現
    ↓
修復 CLAUDE.md（或 slash command、hook）
    ↓
未來所有 session 自動繼承修復
    ↓
所有團隊成員自動繼承修復
    ↓
複利效應：每次改善 × 未來 N 個 session × M 個人
```

## Boris 的三條複利飛輪

### 1. CLAUDE.md 複利
```
Claude 做錯 → 當下花 30 秒加進 CLAUDE.md
→ 下次不重複 → 再下次不重複 → 永遠不重複
```
- 全團隊 CLAUDE.md check in 到 Git
- 多人共同維護，知識在組織中累積
- 新成員、新 session 自動繼承所有過去學到的教訓

### 2. Code Review × @.claude 複利
```
Code Review 中發現問題
→ 留言：「nit: use string literal, not ts enum @claude add to CLAUDE.md」
→ Claude 自動更新 CLAUDE.md
→ 未來所有 PR 自動避免此問題
```
- 每次 code review 不只是修一個 bug，而是**更新了整個系統的記憶**
- [[Claude Code與Git整合工作流]] 的 GitHub Actions 實現

### 3. Slash Commands 複利
```
常做的事情 → 寫成 slash command → 存入 .claude/commands/ → 全團隊共用
```
- `/commit-push-pr`：一個命令完成 commit → push → PR
- `/go`：測試 → 簡化 → 建立 PR 的完整工作流
- `/loop`：設定定期任務（每 5 分鐘、30 分鐘...）

## 為什麼是「複利」而不只是「自動化」

| 一般自動化 | 複利工程 |
|-----------|---------|
| 執行固定動作 | 每次改善後，執行更聰明的動作 |
| 節省線性時間 | 節省指數增長的引導成本 |
| 個人受益 | 團隊全員受益 |
| 一次性設定 | 持續累積、自我強化 |

## 實踐方法

### 立即可做的事
1. **觸發型 CLAUDE.md 更新**：Claude 犯錯的當下，立刻加入 CLAUDE.md，不要說「下次再說」
2. **@.claude code review 習慣**：code review 留言時加上 `@.claude add to CLAUDE.md`
3. **建立第一個 slash command**：把最常做的操作（如 commit+push+PR）寫成一個命令

### 判斷是否值得複利化
- 這件事我是否**這週做了兩次以上**？→ 值得建立 slash command
- 這個錯誤 Claude **是否不止一次犯**？→ 值得加進 CLAUDE.md
- 這個任務 **未來 30 天是否還會出現**？→ 值得建立 `/loop` 定期任務

## 複利工程 vs 複利投資

Boris 明確援引複利投資的比喻：「每一次小的改進都像在存本金，利息是你未來節省的時間和引導成本。」

關鍵差異：
- 投資複利：本金存好就自動滾
- 工程複利：需要有意識地把「改善」系統化（寫進 CLAUDE.md、變成 command），否則只是一次性修復
